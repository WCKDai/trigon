# Window and door schedules

`schedule.openings` is a read-only inventory of the actual built window and door occurrences.
Studio, the CLI and MCP use the same deterministic engine data. It does not change the document,
dirty flag, journal, undo or redo history. Existing local project files need no migration.

In Studio, open **Schedules**. The toolbar's phase/filter controls apply to the inventory;
search and building/storey/kind filters narrow the table and recalculate its totals. Select an
element ID to use the existing Properties controls while the table stays visible. **Show in 3D**
returns to the model and frames the same element. The worker derives the inventory and picking
scene from one geometry build, and invalidates the table while edits or phase changes rebuild it.
Undo and Redo refresh the inventory. Duplicate IDs cannot be selected or edited, even when search
hides one occurrence. Historical and demolished openings remain read-only because the editing
commands target the active phase. Generated interior/cellar doors are inspectable; their existing
authoring limitations still apply. Selecting a row preserves the current plan's storey; only
**Show in 3D** changes the drawing workspace.

```sh
trigon run --doc model.trigon schedule.openings
trigon run --doc model.trigon schedule.openings '{"building":"b1","levels":[0,1],"phase":"forslag","filter":"complete"}'
trigon run --doc model.trigon schedule.openings > out/openings.json
trigon run --doc model.trigon schedule.export '{"path":"out/openings.csv","levels":[0,1]}'
```

The response includes the resolved phase, filter, `rows` and `totals`. Each row contains the
exact built fill `id`, `building_id`, `building_name`, `host_id`, `level`, `level_name`, `kind`
(`window` or `door`), `type_id`, `name`, `status`, `external`, `width_mm`, `height_mm`, `area_m2`
and `quantity_basis`. These are occurrence dimensions, including placement overrides and the
actual built interior-door widths after wall joining. Interior and cellar door types can be
generated by the model without an entry in the editable component library.

`schedule.export` accepts `.json` (the exact query result) or UTF-8 `.csv` with the same filters.
CSV includes units in the headings and phase/filter on every row. Fields containing commas,
quotes or newlines are quoted; formula-like textual cells receive a leading apostrophe. JSON
retains the exact original strings. Invalid queries cannot replace an existing file, and
exporting does not change the document or its history.

For `outer_lining`, area is width × height / 1,000,000 m², matching the IFC window/door base
quantities. This is the complete rectangular unit, including a compound door/window, rather
than clear passage or glazing area. Loggias retain their facade-hole width and height with
`quantity_basis: "facade_opening"` and `area_m2: null`; they do not add a misleading lining area.
Their `kind` follows the existing built model (currently a door). Totals count windows, doors
and all instances, sum included areas and report `area_excluded` separately.

Rows are sorted by building, storey, kind, type, ID, status, host and dimensions. Every occurrence
is retained: phase replacements can share the same built ID even with the same type. Consumers
must not deduplicate by ID or assume it uniquely identifies a row in an `all` view. Studio must
resolve type/status as well, or refuse ambiguous selection/editing.

`building` defaults to all buildings. `levels` defaults to all storeys; an empty list returns
no rows, and duplicates do not duplicate occurrences. Up to 256 level entries are accepted.
Every requested level must exist in every selected building; filter to a building first when
buildings have different storey counts. Unknown buildings, phases, filters, invalid levels and
unknown request fields are errors.

Phase/filter defaults match drawing and IFC exports. Facade placements follow their phase
lifetimes. The existing model always builds interior and cellar doors as `existing`, including
in a `new` view; the schedule preserves that inherited behavior to match the IFC export. No
separate phase assignment for those generated doors is introduced here. Cross-storey windows
are counted once as fills, not once per wall void.

The typed APIs `opening_schedule(doc, view)` and `opening_schedule_from_built(doc, built)` return
`OpeningSchedule`; the latter reuses a background worker's built view without rebuilding geometry.
`retain(building, levels)` filters a result and recalculates its totals. UI callers invalidate
cached schedules when the model or phase view changes, and must not show an old result as current.

Verification covers IFC occurrence counts and lining-area totals across every sample phase/filter,
placement overrides, generated interior/cellar doors, loggia exclusion, same-ID replacements,
multiple buildings, filters, deterministic ordering, hostile dimensions, read-only queries and
refresh after copy/type edits and undo/redo. Commercial application schedule import remains a
separate validation task.

Studio was also checked with the synthetic sample in a running macOS window through its control
protocol: selecting a table row populated Properties with the same ID, the Windows filter showed
39 rows, copying an opening changed the table from 55 to 56 rows, clicking Undo restored 55, and
Show in 3D selected and framed that opening. Native window screenshots verified the rendered table
and model highlight. These checks use Studio's `ui.click` events; physical OS mouse input, Linux
execution on Alpha and large-model performance remain unverified. The engineering kit is absent,
so its additional checks were unavailable; the repository's Cargo gates ran locally.

The offline example also writes `opening-schedule.json` and `.csv` next to the sample project and checks
that copying an opening increases the schedule count from 55 to 56, Undo restores it exactly,
and both independent IFC readers agree with the schedule's window/door counts:

```sh
cargo run -p trigon-engine --example drawing-workflow --locked -- out/drawing-workflow
```
